# Contributing to AMR Agent Kit

Thank you for improving AMR Agent Kit. This repository contains agent skills for Redis application and AI coding best practices plus Azure Managed Redis infrastructure. Keep contributions focused on Azure Managed Redis and Redis application guidance.

## Repository layout

```text
skills/
  redis-code/
  azure-redis-infra/
packages/
  amr-agent-skills-build/
docs/
```

Each skill contains:

- `SKILL.md`: human-readable skill summary and activation guidance.
- `README.md`: skill documentation.
- `metadata.json`: version, organization, date, abstract, and references.
- `rules/`: source rule files and section metadata.
- `AGENTS.md`: generated compact rule index. Do not edit this file directly.

The build uses 32 KiB as a cross-tool compatibility budget for both each generated index and the repository-root plus nested-skill instruction chain. This is based on the lowest published relevant bound: Codex's configurable default `project_doc_max_bytes`. GitHub Copilot, Claude Code, and Gemini CLI currently publish no lower hard limit for this mechanism. The Codex limit applies to the combined discovery chain, and user-level instructions or custom configuration can reduce or increase the effective remaining budget. See [OpenAI's AGENTS.md discovery documentation](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

## Versioning and metadata

- The root `package.json` is the canonical repository identity for the AMR Agent Kit bundle: package name `amr-agent-kit`, display name `AMR Agent Kit`, and current version `1.0.0`.
- Keep plugin manifests aligned with the root package for `name`, display name, `version`, `author`, `license`, `repository`, `homepage`, and Redis/Azure Managed Redis keywords where each plugin schema supports them.
- The GitHub Copilot plugin is the exception to the naming rule. It's named `amr` in the root `plugin.json` and in `.github/plugin/marketplace.json`, and the marketplace is named `amr-agent-kit`. Customers install `amr@amr-agent-kit`, so don't rename either one. Keep the catalog entry `version` equal to `plugin.json`; `npm test` checks this.
- `packages/amr-agent-skills-build/package.json` is the independently named build-tool package. Keep its version aligned with the root package for repo-level releases, but allow it to diverge for tooling-only releases.
- Skill `metadata.json` versions are per-skill content versions. They may advance independently when a skill's rules, `SKILL.md`, README, or generated `AGENTS.md` changes materially. The existing skills are aligned at `1.0.0` for the initial stable bundle.
- Follow SemVer: patch for corrections and clarifications, minor for backward-compatible new or expanded guidance, and major for breaking packaging, activation, or rule-organization changes.
- Do not add a separate `VERSION` file unless a downstream distribution channel cannot read `package.json`; avoid maintaining duplicate version sources.

## Adding a rule

1. Pick the right skill:
   - `redis-code`: Redis application and AI coding patterns, including data structures, commands, caching, messaging, resilience, connection handling, vector search, RAG, semantic caching, LLM memory, embeddings, AI agents, and AI framework integration on Redis.
   - `azure-redis-infra`: Azure Managed Redis provisioning, networking, security, availability, geo-replication, durability, performance, and observability.
2. Choose the correct filename prefix from the skill section map:
   - `redis-code`: `ds-`, `key-`, `cmd-`, `conn-`, `cache-`, `use-`, `msg-`, `stack-`, `memory-`, `resilience-`, `vec-`, `search-`, `rag-`, `semcache-`, `llm-`, `agent-`, `embed-`, `integrate-`, `perf-`
   - `azure-redis-infra`: `provision-`, `network-`, `security-`, `availability-`, `geo-`, `durability-`, `performance-`, `observability-`
3. Copy `rules/_template.md` in the target skill.
4. Name the file in kebab case, for example `cache-prevent-cache-stampede.md`.
5. Add frontmatter with `title`, `impact`, optional `impactDescription`, and `tags`.
6. Include a short explanation, an incorrect example, a correct example, and references to official Redis or Microsoft Learn documentation where possible.
7. Keep examples practical for agent use. Prefer complete, minimal code snippets over abstract advice.

## Improving an existing rule

- Preserve the rule intent unless the change is explicitly a rename or replacement.
- Improve correctness first, then clarity, then breadth.
- Keep Azure Managed Redis assumptions current, especially authentication, TLS, Private Link, module/runtime versions, and cluster policy behavior.
- Avoid unrelated formatting churn.
- If a rule changes behavior or guidance materially, update the skill `README.md` or `SKILL.md` if the summary becomes stale.
- Do not edit generated `AGENTS.md` directly. Regenerate it with the build command.

## Creating a new skill

Create a new directory under `skills/` using kebab case and include:

```text
skills/{skill-name}/
  SKILL.md
  README.md
  metadata.json
  rules/
    _sections.md
    _template.md
```

Then update build configuration in `packages/amr-agent-skills-build/src/config.ts` so the skill can be compiled. Use concise `SKILL.md` activation language and place detailed guidance in rule files.

## Build and validate

From the build package:

```bash
cd packages/amr-agent-skills-build
npm install
npm run build
npm run validate
lychee --config .lychee.toml .
```

The link check requires [Lychee](https://github.com/lycheeverse/lychee) on `PATH`. Install it with the supported package manager for your platform, such as `winget install --id lycheeverse.lychee` on Windows. CI installs Lychee through `lycheeverse/lychee-action` and uses [.lychee.toml](.lychee.toml) for repository-wide Markdown link and fragment checks.

From the repository root, run `npm run validate` for both skill structure and distribution confidentiality, and `npm test` for confidentiality/distribution, copy-button, and generated-output regressions. The ZIP inventory test requires Windows PowerShell (`powershell.exe`) on Windows or PowerShell 7 (`pwsh`) on Linux; both CI runners provide the appropriate executable. Build and validation must leave both generated `skills/*/AGENTS.md` indexes tracked and unchanged from `HEAD`, including staged changes. Unrelated untracked files do not fail this freshness gate.

## Distribution confidentiality review

The confidentiality check is a lint over the distribution boundary, not the private repository as a whole. It uses npm's dry-run package inventory and the same skill and manifest selection as the release ZIP workflow, including published paths and filenames. Build generated skill output before running it. New packaging inputs must be represented by the shared inventory. The Copilot plugin marketplace installs from the repository root, so it publishes the repository itself rather than a separate artifact and isn't part of this inventory.

Product-generation shorthand is a blocker; use AMR or ACRE instead. Source filenames and source path-and-line references are warnings for manual review, not automatic failures. The check reports binary artifacts whose paths were inspected but whose contents were not, and it cannot identify arbitrary semantic disclosures. A passing result is not proof that content is safe to publish.

Before distribution, review the content manually:

- State customer-observable behavior using public evidence.
- Do not expose private implementation explanations merely because internal code confirms them.
- Use AMR/ACRE product names.
- Review source-reference warnings and binary artifacts.
- Confirm every packaging addition appears in the shared distribution inventory.

Useful targeted commands:

```bash
npm run build-redis-code
npm run build-azure-redis-infra
npm run test:confidentiality
```

Before opening a pull request:

1. Run the relevant build command.
2. Run validation.
3. Run link validation.
4. Review generated `AGENTS.md` diffs for ordering, links, and size.
5. Confirm no unrelated generated or documentation files changed.

## Adding eval tasks

Use evals to check whether agents apply AMR Agent Kit guidance in realistic prompts. If an eval harness exists in your branch, add tasks that:

- Exercise one clear Redis or Azure Managed Redis decision.
- Include enough context for the agent to choose the right skill.
- Define expected behaviors and anti-patterns.
- Cover positive and negative cases when practical.
- Avoid provider credentials, secrets, live customer data, or tenant-specific details.

Suggested eval categories:

- Redis data structure selection and key design.
- Connection handling with TLS and Microsoft Entra authentication.
- Vector search, RAG, semantic caching, and LLM memory patterns.
- Azure Managed Redis Private Link, diagnostics, persistence, high availability, and geo-replication.

## Pull request checklist

- [ ] Scope is limited to AMR Agent Kit content.
- [ ] Scope remains limited to Redis and Azure Managed Redis guidance.
- [ ] Rule files use valid frontmatter and approved prefixes.
- [ ] Generated files were changed only through the build.
- [ ] Build and validation commands were run, or the PR explains why they were not needed.
- [ ] CHANGELOG.md has a dated entry for user-facing changes.
